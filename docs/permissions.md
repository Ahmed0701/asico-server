# Permissions

Who may do what. The routes each permission opens are listed here; the same routes, with their headers, are in [api.md](api.md). A test (`tests/docs/permissions.docs.test.ts`) fails when this page and the code disagree about a permission, the routes behind it, or a dashboard card's needs.

## Roles

| Role       | What it gets                                                                                                                                                                                                  |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ADMIN`    | Every permission, implied by the role: no `UserPermission` rows exist for an ADMIN, and the permissions an ADMIN's profile lists are all of them. There is at most one ADMIN. An ADMIN cannot be deactivated. |
| `EMPLOYEE` | Only the permissions an administrator grants, one row each. A new account (from `POST /auth/signup`) is an inactive EMPLOYEE with none.                                                                       |

A request is checked in this order: a valid access token (401 `UNAUTHORIZED`, or 401 `TOKEN_EXPIRED` when it has expired and should be refreshed), an account that exists and is active (otherwise the same 401 `UNAUTHORIZED`), then the permission of the route (403 `FORBIDDEN`). The role and the permissions are read from the database on each request, so a change by an administrator, or a deactivation, takes effect at once and not when the token expires.

Granting is its own permission: `permissions:assign` opens the three permission routes, and is also needed to create a user _with_ permissions in the same request (`POST /users` with a `permissions` list). Without it the request answers 403 `PERMISSION_ASSIGN_REQUIRED`.

### Things the table does not make obvious

- **`villas:read` opens the list, the options and the filters, not one villa.** One villa (`GET /villas/:id`) is `villas:detail`: it shows the parties' phone numbers, the phases and who created it. A role that may browse the list but not open a villa is deliberate.
- **The exports of the areas, the contractors and the civil and electrical engineers use `:read`**, not `:export`: whoever may see the list may export it. The other exports have their own `:export` permission. The contractor's summary and its export are `contractors:summary`; the summary's figures sections (`openWorks`, `smallWorks`, `dailyReports`, `labour`) are each `null` unless the caller also holds the read permission of that resource (`open-works:read`, `small-works:read`, `daily-reports:read`, `daily-labour:read`; an ADMIN holds them all).
- **`:import` opens the template too**, so one permission covers the whole import: download the file, check it with `?dryRun=true`, import it. It does not open the list.
- **Progress and inspection are separate from editing a villa.** Setting a phase's progress is `villas:progress`; putting a villa on the MEW follow-up, MEW inspection and MEW inspection passed lists (and taking it off), and setting its MEW states, is `villas:inspection`. `villas:update` opens neither.
- **Importing villas is its own permission, and `villas:create` does not open it.** `villas:import` loads many villas from a spreadsheet at once, each with its progress rows and its `villa.create` audit entry; give it to the people who load the client's list, not to everyone who may add a villa by hand.
- **Activating and deactivating a user are `users:deactivate`**, not `users:update`. `users:update` also opens the reset-password route.
- **Documents:** upload is `villa-documents:upload`; the list of a villa's documents and the download are both `villa-documents:download`.
- **A list does not hide rows.** Every permission is all-or-nothing for its resource: there is no "only my villas". Filtering by what a user may see is not part of the model.

## The dashboard

`dashboard:read` opens both dashboard routes. `GET /dashboard/summary` is then worked out card by card: a card is computed only for a caller who holds **every** permission listed for it (an ADMIN holds them all), and is `null` in the answer otherwise, so the page can hide it. A card with nothing to count is not `null`: it holds zeros. The recent activity (`GET /dashboard/recent-activity`) lists the latest audit entries, in the same shape as an audit list item, to anyone with `dashboard:read`; the audit log itself, with its filters, detail and export, stays behind `audit:read`.

| Card                | Needs                             |

| `topContractors`    | `villas:read`, `contractors:read` |
| `openWorks`         | `open-works:read`                 |

| `labour`            | `daily-labour:read`               |

The `villas` card carries the keys `villas`, `progress`, `overdue`, `upcoming`, `mewFollowUp`, `mewInspection` and `byArea`; they are all `null` together. The shape is in [frontend-contract.md](frontend-contract.md#dashboard).
